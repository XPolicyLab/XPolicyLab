# Integration validation

Validation performed on Windows, 2026-11-13, against XPolicyLab base `6baccd57ff958570d0db1588370289ee36c8bb70`.

- Six standard-library transport tests passed: two episode boundaries retain the same ledger and generated faculty; absent memory fails without initializing an empty chain; invalid targets are rejected; the remote broker enforces authentication and one active session; non-loopback plain HTTP is refused; a closed episode with an unanswered request cannot block a later episode or receive a stale action. These tests use synthetic state, not a cryptographic or robot benchmark. The closed-episode guard was added after the native trial; it changes the interactive file observer, not the executor or task policy.
- Python compilation and shell syntax checks passed. Adapter-owned code contains no custom image decoder, image encoder or channel swap.
- A local native `stack_bowls`, seed 0 diagnostic reached the new adapter through the normal XPolicyLab imports and existing RoboDojo Cartesian executor. It used the populated live skill, one simulator environment, a local Windows rendering/pipe compatibility launcher, and `L4_INSPECT_MAX_LLM_CALLS=0`. No model process was launched. The native client exited 0; its log reported `0 llm calls` and normal evaluation completion. The agent stopped immediately, producing one failed zero-score diagnostic episode. This is expected for the zero-call check, is excluded from performance claims, and does not validate task-solving ability or Cartesian motion quality. The existing Timechain ledger was unchanged.
- Generic debug plain/encoded loops are **not passed**: the shared debug `TestEnv` does not provide the `robot_manager`/Cartesian planner the inherited EEF executor requires. Native simulator testing is the appropriate next gate for model-selected motion.
- A subsequent **local, previously seen-layout integration trial** used the existing interactive root agent and populated live skill, without launching another model. On `stack_bowls`, seed 0, layout 0, the native result was **score 100.0, success true**, one episode. It used 17 action decisions and 370/800 native steps; native exit was 0. Three success videos each contain 387 frames. The robot and Timechain continued through the new adapter; memory tip advanced from ring 12058 during preparation to ring 12075 at episode end, without reset. The earlier successful trajectory for this exact public layout was available and reused, with fresh RGB and arrival checks. This is not an unseen-layout/generalization result, a matched skill comparison or an official score. Native `17 llm calls` counts adapter tool-reply requests, not independently measured provider API inference calls.
- The interactive host's actual model identifier could not be independently verified. The configured environment label `gpt-6.1-sol/xhigh` is the intended CLI submission target, not proof of this interactive host's immutable model identity. `run_agent.py`'s actual continuing CLI session has not yet been validated. Two model-authored perspective comparisons were sealed across preparation/placement; routine motion audits used the same explicit six-score vector, so those repeated audit scores are not evidence of per-action calibration. Two inappropriate replay suggestions were explicitly rejected rather than blindly executed.
- Workflow limitation: the first action reply was written at approximately 21:52:37 UTC while its full-loop command was still running; that turn's ring 12059 was sealed at approximately 21:53:48 UTC. A prior strategy fork and chain verification had passed, but this is not a claim of complete pre-action loop adherence. Later decisions used the explicit verify/genesis/recall/faculty-label/PoQ path. These limitations reinforce that this is an integration check, not a controlled evaluation of skill effectiveness.
