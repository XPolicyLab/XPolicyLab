# Q0-Preview installation and environment setup

Q0-Preview runs an Agent that calls a remote model API, executes Python tools in a local sandbox and sends action plans to a GPU motion controller. Model weights are hosted by the API provider; no local model checkpoint or training environment is needed.

This is the installation guide for all three components. Prepare the [workspace layout](#workspace-layout), then follow these steps:

1. [API configuration](#api-configuration): choose the model endpoint and supply credentials.
2. [Tool use environment](#tool-use-environment): install the Agent and prepare its Python sandbox.
3. [Controller environment](#controller-environment): prepare CuRobo and the GPU policy service.
4. [Evaluator settings](#evaluator-settings): connect RoboDojo observations and actions, then complete [Verification](#verification).

| Component | Runs in | Requirements |
| --- | --- | --- |
| API calls and Agent orchestration | Agent host process | Python 3.11, API network access and credentials |
| Python tools | Local CPU sandbox | Python dependencies, Docker and a mountable Python prefix; no network or GPU inside the sandbox |
| Motion planning and execution | Policy service on the host | Python 3.11, NVIDIA GPU and compatible CuRobo/PyTorch/CUDA packages |

Run the commands in Bash on Linux x86_64, from the XPolicyLab checkout root unless another directory is specified. The setup uses Conda and Git. Docker is required for the default tool sandbox, and the Controller requires an NVIDIA GPU with a compatible driver.

The Agent and policy service may share a compatible Python environment. The commands below use separate environments so each can be prepared independently. RoboDojo, its simulator assets and its evaluator environment are supplied separately by the evaluator.

## Workspace layout

The adapter uses XPolicyLab's shared helpers and the benchmark workspace's environment configuration:

```text
<benchmark-workspace>/
├── env_cfg/
│   ├── arx_x5.yml
│   └── robot/_robot_info.json
├── XPolicyLab/
│   ├── setup_policy_server.py
│   ├── utils/
│   └── policy/Q0_Preview/
└── ...                         # evaluator source and simulator assets
```

Use the evaluator's existing RoboDojo workspace and follow its own setup instructions for simulator assets and environment configuration. `env_cfg/` is not generated by this adapter.

The adapter is located at [XPolicyLab/policy/Q0_Preview](./). For a fresh checkout inside the benchmark workspace:

```bash
git clone https://github.com/XPolicyLab/XPolicyLab.git XPolicyLab
cd XPolicyLab
```

If the workspace already contains the official XPolicyLab checkout, use its `policy/Q0_Preview/` directory. Keep the complete adapter tree, including `assets/`, `controller/` (with `calibration/`), `runtime/`, `config/`, `harness/` (with `helpers/`) and `tools/`.

The current Agent launcher searches for `XPolicyLab/utils/process_data.py` beneath the workspace parent. A checkout named only `Q0-Preview` does not satisfy that lookup. For a separate official checkout, `Q0_PREVIEW_XPL_ROOT` names its **parent**, not the checkout itself:

```bash
export Q0_PREVIEW_XPL_ROOT=/absolute/path/to/benchmark-workspace
test -f "$Q0_PREVIEW_XPL_ROOT/XPolicyLab/utils/process_data.py"
```

## API configuration

The Agent host sends HTTPS requests to the configured model endpoint. API calls use Python's standard-library HTTP/SSL support and `certifi`; no model-provider SDK is required. Network access is needed on the Agent host, while Python tools run in a sandbox with networking disabled.

Choose one configuration below and export its settings in the shell used to launch the policy. These commands configure access without making an API request.

| Configuration | Model | API |
| --- | --- | --- |
| [config/agent.opus55.json](config/agent.opus55.json) (default) | `claude-opus-5-5` | Anthropic Messages; appends `/v1/messages` to the endpoint base |
| [config/agent.gpt6astra.example.json](config/agent.gpt6astra.example.json) | `gpt-6-astra` | OpenAI Responses; appends `/responses` to a base such as `https://api.openai.com/v1` |

### Select an API configuration

For Opus:

```bash
mkdir -p "$HOME/.config/q0-preview"
cp -n policy/Q0_Preview/config/agent.opus55.json "$HOME/.config/q0-preview/agent.json"
export Q0_PREVIEW_AGENT_CONFIG="$HOME/.config/q0-preview/agent.json"
export Q0_PREVIEW_API_BASE_URL='https://YOUR_API_ENDPOINT'
read -rsp 'API key: ' Q0_PREVIEW_API_KEY; echo
export Q0_PREVIEW_API_KEY
```

The Opus example uses Anthropic Messages. Supply the base before `/v1/messages`, because the transport appends that suffix.

For GPT-6 Astra, select the separate example and an OpenAI API credential:

```bash
mkdir -p "$HOME/.config/q0-preview"
cp -n policy/Q0_Preview/config/agent.gpt6astra.example.json "$HOME/.config/q0-preview/agent.gpt6astra.json"
export Q0_PREVIEW_AGENT_CONFIG="$HOME/.config/q0-preview/agent.gpt6astra.json"
export Q0_PREVIEW_API_BASE_URL='https://api.openai.com/v1'
read -rsp 'OpenAI API key: ' Q0_PREVIEW_API_KEY; echo
export Q0_PREVIEW_API_KEY
```

Use the same `eval.sh` command for either configuration. The launcher enables OpenAI transport from the selected configuration. Astra uses [OpenAI Responses](https://developers.openai.com/api/docs/models/gpt-6-astra) for image input and function calls; the endpoint must support `POST /v1/responses`. For a compatible gateway, set its API base including any `/v1` prefix; the adapter appends `/responses`. Keep `stream: false` for this transport. A Chat Completions-only gateway is insufficient for Astra tool calls; see the [reasoning guide](https://developers.openai.com/api/docs/guides/reasoning).

Environment variable `Q0_PREVIEW_API_BASE_URL` takes precedence over JSON `base_url`; update it when switching providers. Credentials are read from the environment variable named by `api_key_env` (default `Q0_PREVIEW_API_KEY`); configuration files must not contain credential literals.

`Q0_PREVIEW_AGENT_CONFIG` selects a complete configuration file, not a partial overlay. The launcher supplies the Agent prefix from `Q0_PREVIEW_AGENT_PREFIX` or the active policy environment, overriding a `python_prefix` in JSON. Each configuration uses one model and credential for both planning and checkpoint review. There is no automatic switch to a different model after an API error. Prompt content, task definitions, tool schemas, control logic and episode budgets are shared; model performance must be evaluated separately.

### Transport and generation settings

The Opus configuration uses adaptive thinking, streaming and explicit prompt-cache settings. The Astra configuration uses non-streaming Responses requests with images and function calls. Both use `xhigh` effort for planning and `low` for isolated checkpoints, with output limits of 49,152 and 1,536 tokens respectively.

| Setting | Opus configuration | Astra configuration |
| --- | --- | --- |
| Streaming | `true` | `false` |
| API request timeout | 3,600 seconds | 3,600 seconds |
| HTTP idle timeout | 180 seconds | 3,600 seconds |
| Network recovery window | 600 seconds | 600 seconds |

Astra's longer HTTP idle timeout allows a non-streaming response to remain silent while generating. The request timeout and remaining planning/checkpoint deadline still cap each call. Network recovery is capped by the remaining planning window. These API transport settings are separate from the evaluator's response wait limit. Astra task success rates require separate evaluation; adding the interface does not establish equivalent model performance.

## Tool use environment

The Agent host process runs the model/tool loop and needs the adapter and shared XPolicyLab dependencies. Its Python tools use NumPy and SciPy for geometry, Pillow and OpenCV for images, and Matplotlib for plots. Their dependencies are installed from [requirements.txt](requirements.txt).

### Prepare the Agent Python environment

Create a Linux Python 3.11 prefix containing `bin/python`:

```bash
export Q0_PREVIEW_AGENT_PREFIX="$HOME/.conda/envs/q0-preview-agent"
conda create --prefix "$Q0_PREVIEW_AGENT_PREFIX" python=3.11 pip
conda activate "$Q0_PREVIEW_AGENT_PREFIX"
bash policy/Q0_Preview/install.sh
python -m pip check
```

`install.sh` installs the adapter and shared XPolicyLab dependencies with the active `python`. To reuse an existing compatible prefix, set `Q0_PREVIEW_AGENT_PREFIX` to its absolute path, skip `conda create` and run the installation and dependency check there. The prefix can also be the policy environment if it works in the sandbox. Keep `Q0_PREVIEW_AGENT_PREFIX` exported when you later activate the policy environment.

The prefix is mounted read-only at `/opt/python`. A virtual environment whose interpreter or libraries link to an unmounted host installation may import successfully on the host and still fail in the sandbox. Check the mount before starting an evaluation.

### Docker sandbox

The default sandbox uses `ubuntu:24.04`, no network, no GPU, two CPUs and a 16 GiB memory limit. Its launcher uses `--pull=never`, so prepare the image while network access is available:

```bash
docker info
docker pull ubuntu:24.04
docker image inspect ubuntu:24.04 --format '{{.Id}}'
```

Record the actual image ID with your environment record. Import-test the mounted prefix using the same library search path as the tool runtime:

```bash
docker run --rm --pull=never --network=none --read-only \
  --cap-drop=ALL --security-opt=no-new-privileges \
  --user "$(id -u):$(id -g)" --tmpfs /tmp:rw,nosuid,size=256m \
  --mount "type=bind,src=$Q0_PREVIEW_AGENT_PREFIX,dst=/opt/python,readonly" \
  --env LD_LIBRARY_PATH=/opt/python/lib \
  --env OPENBLAS_NUM_THREADS=1 --env OMP_NUM_THREADS=1 \
  --env MPLBACKEND=Agg --env MPLCONFIGDIR=/tmp/matplotlib \
  --entrypoint /opt/python/bin/python ubuntu:24.04 \
  -c 'import numpy, scipy, cv2; from PIL import Image; import matplotlib; assert numpy.__version__ == "1.26.4"; print("Sandbox imports passed")'
```

This checks the mounted Python dependencies without invoking a model API. Bubblewrap remains an explicitly configured alternative; Docker is the default recipe.

## Controller environment

The Controller uses CuRobo to turn validated action plans into robot joint actions. Its GPU stack runs in the policy service, outside the Python-tool sandbox. Choose one of the following installation paths, then run the GPU check below. This step activates the policy environment used for evaluation.

### Use an existing compatible environment

Activate the environment containing the required CuRobo/PyTorch/CUDA stack, then install the adapter:

```bash
conda activate q0-preview-policy
bash policy/Q0_Preview/install.sh
python -m pip check
```

Replace `q0-preview-policy` with the existing environment name. The GPU stack must provide the CuRobo interfaces shown in the GPU check below. `install.sh` installs the adapter and shared XPolicyLab dependencies; it does not provision the GPU stack, Docker or the evaluator.

### Create a policy environment

Prerequisites are Conda, Git, an NVIDIA driver compatible with CUDA 12.8, and access to the package indexes and pinned source revision. The CUDA Python package versions in the constraints file are not system CUDA toolkit version requirements.

Create a separate policy environment:

```bash
conda create -n q0-preview-policy python=3.11 pip
conda activate q0-preview-policy
python -m pip install 'torch==2.7.0' --index-url https://download.pytorch.org/whl/cu128
python -m pip install \
  -c policy/Q0_Preview/config/policy-runtime.constraints.txt \
  'nvidia-curobo[cu12] @ git+https://github.com/NVlabs/curobo.git@895c6517243f8cb091c73c018c8167192d39599a'
PIP_CONSTRAINT="$(pwd)/policy/Q0_Preview/config/policy-runtime.constraints.txt" \
  bash policy/Q0_Preview/install.sh
python -m pip check
```

The CuRobo package name and CUDA extra are declared in the [pinned source metadata](https://github.com/NVlabs/curobo/blob/895c6517243f8cb091c73c018c8167192d39599a/pyproject.toml). Use this source revision with the PyTorch CUDA 12.8 wheel and the version constraints above. An older CuRobo API or a different source revision may not provide the required planner interfaces. If dependency resolution fails, check the reported conflict against the dependency files before changing versions.

### Check the GPU environment

Check the selected Python, GPU visibility and required CuRobo interfaces:

```bash
python - <<'PY'
import sys
import numpy
import torch
from curobo.batch_motion_planner import BatchMotionPlanner, MotionPlannerCfg
from curobo.inverse_kinematics import InverseKinematics, InverseKinematicsCfg
from curobo.motion_planner import MotionPlanner
print('Python:', sys.version)
print('NumPy:', numpy.__version__)
print('PyTorch / CUDA:', torch.__version__, torch.version.cuda)
assert numpy.__version__ == '1.26.4'
assert torch.cuda.is_available(), 'CUDA is unavailable in this policy environment'
print('GPU:', torch.cuda.get_device_name(0))
PY
```

This checks imports and CUDA visibility only. GPU kernel compilation, planner warmup and a short joint-space plan must also succeed on the deployment host before a full evaluation.

## Evaluator settings

The [observation interface](docs/OBSERVATION_INTERFACE.md) documents the calibration hook for official integration, including USD/OpenGL camera axes and current-frame wrist extrinsics. A deployment without this hook must expose the required matrices before normal evaluation; configuration flags alone are insufficient if its observation implementation does not support them.

Before simulation, confirm that the external evaluator provides:

- `arx_x5` joint actions at 25 Hz and one environment per policy service.
- All three RGB cameras, intrinsic matrices and current camera-to-world extrinsics.
- Joint/gripper state, world-frame end-effector poses and the task instruction.
- The workspace's `env_cfg/arx_x5.yml` and corresponding robot registration.

The episode planning budget and the default policy-response wait limit are both 10800 seconds (3 hours). The episode budget is `wall_seconds: 10800`, counted from the first observation. The launcher exports `ROBODOJO_POLICY_REQUEST_TIMEOUT_S=10800` for the response wait limit. The evaluator must read this variable and pass it as `ModelClient(request_timeout_s=...)`; otherwise, the XPolicyLab client's built-in request timeout of 120 seconds applies.

## Runtime configuration

| Environment variable | Purpose |
| --- | --- |
| `Q0_PREVIEW_AGENT_PREFIX` | Agent Python environment; defaults to the active policy environment |
| `Q0_PREVIEW_AGENT_CONFIG` | Optional complete Agent configuration file; use an absolute path outside the package |
| `Q0_PREVIEW_API_BASE_URL` | HTTPS endpoint base; overrides `base_url` in the Agent configuration |
| `Q0_PREVIEW_API_KEY` | Credential read by the default `api_key_env`; never put the key in JSON |
| `Q0_PREVIEW_XPL_ROOT` | Optional parent of a checkout named `XPolicyLab`, used to locate shared helpers |
| `Q0_PREVIEW_RUN_ROOT` | Output parent; defaults to checkout-local `runs/Q0_Preview` |
| `Q0_PREVIEW_RUN_DIR` | Optional exact, new run directory; overrides `Q0_PREVIEW_RUN_ROOT` |

The normal service launcher explicitly overrides the four episode budgets with its CLI defaults. Editing those values only in `deploy.yml` does not change normal `eval.sh` runs. Debug mode reads `deploy.yml` directly. Keep the documented defaults for the standard evaluation recipe; see the [budget table](README.md#configuration).

## Verification

With the policy environment active, check the installed entry points from the XPolicyLab checkout root:

```bash
PYTHONPATH="$(pwd)/..:$(pwd)" python - <<'PY'
from XPolicyLab.policy.Q0_Preview.model import Model
from XPolicyLab.policy.Q0_Preview.harness.runner import Agent
print('Policy and Agent imports passed')
PY
```

Complete the [mounted-prefix check](#docker-sandbox) and [CUDA/CuRobo check](#check-the-gpu-environment), then follow [Evaluation](README.md#evaluation) to run the policy with the configured model API. Import checks alone do not verify API access, motion planning or simulator execution.

## Installation files

Use this guide for the setup sequence. The following files provide its executable installation steps and dependency specifications:

| File | Purpose |
| --- | --- |
| [install.sh](install.sh) | Installs adapter dependencies and editable XPolicyLab using the active `python`, then checks basic imports and the NumPy version |
| [requirements.txt](requirements.txt) | Python dependencies for the adapter, API transport and tools |
| Repository [pyproject.toml](../../pyproject.toml) | Shared XPolicyLab dependencies, installed by `install.sh` |
| [config/policy-runtime.constraints.txt](config/policy-runtime.constraints.txt) | Package version constraints explicitly passed to pip when creating the Controller environment |

`install.sh` does not create Conda environments or install CuRobo, PyTorch, CUDA, Docker or RoboDojo. The constraints file restricts package versions; it does not install packages itself, is not a complete lockfile and is not automatically loaded by `install.sh`.

Keep dependency versions and the sandbox image consistent when comparing runs, because they can affect numerical results and Python-tool outputs. The `config/agent.*.json` files configure model access and Agent behavior separately from these Python dependencies.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| `Set Q0_PREVIEW_XPL_ROOT to the parent...` | Checkout name and workspace layout; the variable points to the parent containing `XPolicyLab/` |
| Missing `curobo.batch_motion_planner` or `InverseKinematicsCfg` | CuRobo revision and active policy interpreter; an older API is incompatible |
| Host imports pass but `/opt/python/bin/python` fails | Prefix symlinks, shared libraries and Linux compatibility inside the sandbox |
| Docker reports that the image is absent | Pull the configured image in advance; runtime pulling is disabled |
| Missing Agent imports such as `h5py` | Install the adapter and editable XPolicyLab in the Agent environment too |
| API URL returns 404 | Check the endpoint base and the appended suffix: `/v1/messages` for Opus or `/responses` for Astra |
| `OpenAI transport requires --enable-openai` | Use `eval.sh` with the Astra configuration; a direct invocation of `harness.runner` needs this flag |
| `OpenAI Responses transport requires stream=false` | Use the Astra example's non-streaming setting; the OpenAI transport does not consume SSE |
| Editing `deploy.yml` budgets has no effect | The normal service passes its CLI defaults as overrides; see README configuration precedence |

Each service prints its run directory. Inspect `server.log` there and `sessions/<episode_uuid>/agent.log` for startup failures. API archives and per-observation errors are kept beneath the episode directory. Keep the environment package list and image ID alongside evaluation results when comparing runs.
