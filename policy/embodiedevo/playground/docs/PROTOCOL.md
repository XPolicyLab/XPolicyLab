# Execution and evaluation protocol

The protocol identifier remains `workspace-session-v1`. EmbodiedEvo is the project
name; renaming does not change the experiment semantics.

## Persistent code sessions

An agent writes Python into its workspace and submits it with:

```bash
python scripts/env.py exec submission/solution.py
python scripts/env.py exec submission/solution.py --include skills/helper.py
```

The host executes each submission in the same Python namespace and native
simulation session. The handwritten manual exposes exactly `get_instruction()`,
`get_observation()`, `step(action)` and Playground-only `reset()`.
The task goal comes from the native simulator's instruction.

Feedback contains stdout/stderr, native camera observations/videos, robot state
and the configured success signal. No second model summarizes observations.
The host keeps private rewards, official scores, scene identities and ledgers
outside the agent workspace. [Client details](../orchestrator/session_client.md)
describe requests and feedback.

## Playground to Test

Playground uses its fixed configured scene. It permits same-scene reset, which
renews the native action allowance while preserving Python variables, consumed
execution requests and elapsed time. Skills and Lessons are writable.

At completion, the host freezes only `skills/` and `lessons/`. It then samples
and persists Test scene identities. Each Test starts a fresh agent, workspace
and simulator, with read-only knowledge and no inherited Playground program.
Test allows iterative observation and coding within the current scene. It
forbids reset and transfer between Test scenes. Resume reuses the saved scene
plan and does not silently rerun completed or failed attempts.

The Test-only baseline has its own instruction template and no Playground or
transferred knowledge. Public recipes are supplied task information; their
default inclusion is the same for both task templates. Set
`EMBODIEDEVO_USE_RECIPE=0` before run creation for a recipe-free condition and record
that condition when comparing results.

## Isolation and budgets

The agent container sees only its workspace, staged CLI home and session socket.
It has no simulator sources, assets, private task configuration, GPU, native
policy-server socket or host ledger. Instruction, primitive manual, client and
observations are read-only; Test knowledge is also read-only.

The task templates keep 100 execution requests per session and the native
task-specific action limit. The host renders both limits into the instruction.
`status` reports remaining budgets without advancing physics. Watchdogs and
model settings are recorded in the host configuration.

The direct adapter includes reset compatibility and camera resource cleanup.
The native-evaluator adapter also forwards trial termination and action-limit
information. Describe these adapters when reporting results. Their presence is
not organizer verification of a submission.

## Evidence and failures

Every execution preserves its submitted code and raw feedback under
`workspace/observations/`. Host files retain the pinned configuration, frozen
hashes, timing, model usage and native reports where available. Runtime files
are generated by new experiments; no previous experiment evidence is bundled.

Preserve model-caused failures as failures. Missing reports, timeouts, CUDA
errors and simulator crashes alone do not establish an infrastructure fault.
The runtime's `valid` field describes whether an execution produced its expected
records; a result analysis must additionally classify failures and disclose the
denominator. Do not drop model failures or retry until success. Approved
infrastructure reruns need their original evidence and reason retained.
