# Run the agent on RoboDojo

This tutorial runs the agent (programs, learned skills, reactive layer, handlers,
verifier) on RoboDojo: one development episode, a development subset, and the
evaluation protocol. It assumes the services of your deploy are up
([Quickstart](../getting-started/quickstart.md)).

## Layouts: development first

RoboDojo's official evaluation uses fixed layout packs (`layout_pack_seed` 0, 1, 2).
Prompt work, skill work and self-improvement use **development layouts** instead:
`layouts = "procedural"` replays `<dev_layout_dir>/<task>_<seed>.json`, generated by
`benches/robodojo/devlayouts.py` with RoboDojo's own generator and checked not to
repeat any evaluation layout. Development seeds are unlimited; the same (task, seed)
always gives the same layout.

Three tasks have none: `cover_blocks`, `swap_blocks` and `play_tic_tac_toe` place their
objects at a few fixed spots, and the evaluation packs already hold every arrangement,
so the generator gives up ("repeats evaluation layout") and the worker does not start.
They cannot be developed on without touching evaluation layouts. On
`imitate_sorting_sequence` both development layouts so far are marked unstable by
RoboDojo partway through the episode (about step 460), so those episodes are not
scored.

!!! note
    An experiment with `layouts = "eval"` measures a frozen configuration: it resolves
    strictly, and replaces an unstable layout by the next one, as RoboDojo does.

## One episode

```bash
harness run configs/experiments/dev.toml --deploy mine --output runs/dev
```

```toml
--8<-- "configs/experiments/dev.toml"
```

The agent's default model (`configs/models/deepseek-flash.toml`) is DeepSeek V4.1 Flash
(`deepseek-flash` at `https://api.deepseek.com`). Set `DEEPSEEK_API_KEY`.
`--model qwen3.8-27b` or another file of `configs/models/` replaces it; the paper's
runs name theirs in the experiment.

## A development subset

```toml
--8<-- "configs/experiments/subset8.toml"
```

```bash
harness run configs/experiments/subset8.toml --deploy mine --output runs/subset8 --gpus 5 --workers-per-gpu 2
```

`harness run` starts one simulator worker per slot (GPUs × workers per GPU, 6-9 GB
each), each on its own port from `base_port`, and gives the slots tasks from a queue;
a worker serves one task, then stops. It:

- **resumes**: an episode with a `summary.json` is skipped; `--rerun-errors` runs again
  only the ones that ended in an error (a provider or worker failure);
- **caps spending**: `--max-total-cost-usd` (or `budget.max_total_cost_usd`) starts no
  new episode once the suite has spent that much; a running episode finishes;
- **replaces unstable layouts** on evaluation layouts: an episode RoboDojo marks
  unstable is moved aside (`seed-<n>.unstable-<time>`) and the next free layout runs.

The output is one directory per task and seed:

```text
runs/subset8/
├── suite.json   suite.log   workers/   tmp/
└── stack_bowls/
    ├── seed-0/  manifest.json  events.jsonl  summary.json  kernel.log  videos/
    └── seed-1/  ...
```

## Scores

```bash
harness report runs/subset8
```

`harness report` follows RoboDojo's scoring: an episode scores its reward (1 on
success, else the process score / 100); an error scores 0; an episode the simulator
dropped as unstable is not scored. Tasks pool their `_random` variants; the five
dimensions (Generalization, Memory, Precision, Long-Horizon, Open) average their tasks,
and the overall score averages the dimensions, given only when every task has a score.
It also reports model calls, cost and decisions per episode; `--json` prints
everything. Each episode's `summary.json` records the strategy the model chose
(`strategy`: A, B or C, the kind it matched, the policy).

## The evaluation protocol

```toml
--8<-- "configs/experiments/eval.toml"
```

```bash
harness run configs/experiments/eval.toml --deploy mine --seeds 0-49 --max-total-cost-usd 200 \
  --rerun-errors --output runs/eval-pack0
```

Evaluation layouts resolve **strictly**: if the machine does not run a service the
agent names, the run stops instead of running a smaller configuration (whose identity
would differ). Every episode's `manifest.json` records the identity, so the results of
two machines can be compared, or not.

This runs the agent through our own simulator worker. The leaderboard runs the exported
policy through RoboDojo's own client instead, every task and `_random` variant at the
official episode counts: [Submit to RoboDojo's leaderboard](submit-xpolicylab.md).
Compare an agent with the learned policy it wraps on the same layouts: run the policy
alone (`configs/experiments/policy-alone-dev.toml` with `configs/scripts/policy_alone.json`,
or the same script on evaluation layouts) next to the agent, and pair the tasks.
