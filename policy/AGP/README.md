# AGP

**Contributor:** Mengzhao Jia, Yang Lin, Xixin Zhang, Zhihan Zhang, Xiaobai Liu, Meng Jiang | **Paper:** Agent as Policy for Robotic Manipulation | **arXiv:** https://arxiv.org/abs/2609.12541 | **Original code:** https://github.com/agent-as-policy-2026/agent-as-policy

AGP (Agent-as-Policy) uses an LLM agent as the policy: the codex CLI running `gpt-6-astra` drives both ARX X5 arms through MCP tools (`goal`, `observe`, `measure`, `step`, `run`, `action_status`, `assess`) and a policy-side cuRobo motion planner, from RGB images only. This adapter is evaluation-only: there are no weights, no data processing and no training, and the agent runtime is packaged in `agp_runtime/`.

Shared conventions — argument meanings, checkpoint naming, split-machine deployment, `EVAL_ENV_TYPE` — are documented in the [XPolicyLab README](../../README.md). Official results: [RoboDojo LeaderBoard](https://robodojo-benchmark.com/LeaderBoard).

## Installation

Prerequisites: the official RoboDojo checkout with its submodules, its Assets (with `Assets/Robots/*/curobo.yml` generated by RoboDojo's `utils/update_embodiment_config_path.py`) and its conda environment `RoboDojo`; an NVIDIA GPU with RT cores (Isaac Sim renders with RTX; A100/H100 cannot) with its Vulkan ICD at `/usr/share/vulkan/icd.d/nvidia_icd.json` or `/etc/vulkan/icd.d/nvidia_icd.json`; `/usr/bin/python3` with PyYAML.

```bash
cd XPolicyLab/policy/AGP
bash install.sh --check   # reports what is present and what would be installed; changes nothing
bash install.sh
```

`install.sh` writes nothing into the checkout. Without `--steps` it installs the first three steps:

| Step | Location | Content |
| --- | --- | --- |
| `venv-policy` | `$AGP_HOME/.venv-policy` | the stub policy server's interpreter (XPolicyLab's declared dependencies) |
| `venv-agent` | `$AGP_HOME/.venv-agent` | the MCP server's interpreter |
| `codex` | `~/.codex/packages/standalone/releases/0.160.1-x86_64-unknown-linux-musl/` | the pinned codex CLI release, checked by sha256 |
| `venv-sim` | `$AGP_HOME/.venv-sim` | only with `--steps venv-sim`: the simulator runtime for a machine without RoboDojo's conda environment (about 25 GB) |

`AGP_HOME` (default `~/.agp-robodojo`, never inside the checkout) holds the venvs and everything the runtime writes; use the same `AGP_HOME` for `install.sh` and `eval.sh`. uv and the CPython build the venvs run on go to `AGP_SETUP_DIR` (default `.agp-setup` next to `AGP_HOME`); keep that folder.

## Evaluation

```bash
cd XPolicyLab/policy/AGP
bash eval.sh <bench_name> <task_name> <ckpt_name> <env_cfg_type> <action_type> <seed> \
  <policy_gpu_id> <env_gpu_id> <policy_env> <eval_env>

# Example
bash eval.sh RoboDojo stack_blocks no-checkpoint arx_x5 joint 0 0 0 default RoboDojo

# LLM-free scripted test policy on one layout (no model access needed)
EVAL_NUM=1 AGP_SCRIPTED=smoke bash eval.sh RoboDojo stack_blocks no-checkpoint arx_x5 joint 0 0 0 default RoboDojo

# Offline wiring check (no simulator, no agent)
EVAL_ENV_TYPE=debug bash eval.sh RoboDojo stack_bowls no-checkpoint arx_x5 joint 0 0 0 default RoboDojo

# One complete seed (every task) through RoboDojo's entry point, from the checkout root:
# 12 simulators, three on each of GPUs 0-3 (--only a,b,c selects tasks)
cd ../../..
bash scripts/robodojo.sh benchmark --policy-dir XPolicyLab/policy/AGP --ckpt no-checkpoint --policy-env default \
  --action-type joint --eval-num native --seed 0 --gpu-ids 0,0,0,1,1,1,2,2,2,3,3,3 --run-id agp-seed0
# Seeds 1 and 2: --seed 1 / --seed 2 with their own --run-id; after exit code 3, run the same command again with --resume
bash scripts/robodojo.sh summarize    # writes eval_result/RoboDojo/_summary.md
```

- `env_cfg_type` is `arx_x5` and `action_type` must be `joint`; through `scripts/robodojo.sh` pass `--action-type joint`. `ckpt_name` is ignored; `no-checkpoint` is the placeholder.
- `policy_env`: `default` is `$AGP_HOME/.venv-policy`; a conda environment or a Python with websockets >= 14 also works (RoboDojo's `RoboDojo` environment has websockets 12.0 and cannot run the server).
- `eval_env`: a conda environment, normally `RoboDojo`, in which the simulator runs; `default` uses `$AGP_HOME/.venv-sim`.
- One environment per episode (`eval_batch: false`). The simulator, the agent and the planner run on `env_gpu_id`; the stub server needs no GPU.
- Results go to the checkout's `eval_result/` as for every policy. The scripted test policy writes them to `$AGP_HOME/runs/official/<run id>/` instead, so it never replaces agent results in `summarize`. Logs and the agent sessions are in `$AGP_HOME/runs/official/<run id>/`.
- `EVAL_ENV_TYPE=debug`: `deploy.py` runs the loop of `policy/demo_policy/deploy.py` and `model.py` answers with actions that hold the observed joint state, keyed and sized by `get_robot_action_dim_info(env_cfg_type)`. This checks the wiring, not the agent.

## Model Assets

There is no checkpoint. The agent uses a ChatGPT subscription through the codex login, not an API key. We provide the logins to the organizers as an account pool folder:

```bash
mkdir -p -m 700 ~/.agp-robodojo/private
tar -xzf agp_accounts.tar.gz -C ~/.agp-robodojo/private    # creates private/accounts/
```

Every episode takes one of its logins; the accounts we provide support at most 12 simulators running at the same time. Without the pool folder, every episode uses the login in `~/.codex/auth.json`.

## Configuration

The fixed system is this folder: the agent runtime `agp_runtime/` (the prompt `agp_core/PROMPT.md`, the task notes with each task's official requirements, and a hint for tasks), the model settings in `deploy.yml`, and codex 0.160.1. The same system runs for every task.

`deploy.yml` keys beyond the shared set:

| Key | Value | Role |
| --- | --- | --- |
| `agp.model` | `gpt-6-astra` | codex model |
| `agp.effort` | `high` | codex reasoning effort |
| `agp.service_tier` | `default` | codex service tier |
| `agp.episode_timeout_s` | `14400` | wall-clock limit per episode; at the limit the episode ends as a failure |
| `agp.end_grace_s` | `180` | scripted test policy only: time it keeps after the official episode end |
| `agp.agent_finish_wait_s` | `60` | time for the launcher to exit after the policy finished |
| `agp.runtime_root` | `agp_runtime` | the packaged runtime, inside this folder |
| `agp.codex_binary` | `~/.codex/packages/standalone/releases/0.160.1-x86_64-unknown-linux-musl/bin/codex` | the pinned codex release |

Environment variables: `AGP_HOME` and `AGP_SETUP_DIR` (above); `ROBODOJO_RUN_ID` (the run name); `AGP_SCRIPTED` (`smoke`, `observe` or `idle`: the scripted test policy instead of codex); `AGP_RUNTIME_LIBS` (system libraries unpacked without root).

## Notes

- **Episode.** RoboDojo's eval client calls `eval_one_episode` of `deploy.py` once per layout; the adapter (`agp_runtime/agp_core/official_deploy.py`) runs the episode in that process and its children. The stub policy server holds no model.
- **Observation.** Only the official RGB images of the three cameras and proprioception; no depth and no simulator state. Camera intrinsics and poses come from the public RoboDojo configuration. `TASK_ENV` is wrapped in a whitelist, and every access is logged.
- **Planning.** A cuRobo planner built from the public robot files runs on the policy side; the official step limit is kept.
- **End.** An accepted `assess` ends the episode. If the official episode has not ended by then, the adapter clears `success[0]` and calls `is_episode_end()`, so the evaluator decides with its own final check.
- **Failures.** Infrastructure failures (the agent not starting, login or provider errors, an outside kill) stop the run with exit code 3 and are not counted; re-run with the same `ROBODOJO_RUN_ID` to run only the missing layouts.
- Split-machine deployment brings nothing: codex, the MCP server and the planner all run on the environment-client machine.
- In containers without user namespaces, codex's bubblewrap sandbox cannot start; episodes still run, because the agent works only through MCP tools.
